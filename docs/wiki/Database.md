# Database

Ludarium uses **PostgreSQL** as its only datastore. The schema is owned by **Flyway**
migrations; Hibernate is only allowed to verify it.

> The catalog is no longer a JSON file. `backend/src/main/resources/games.json` and the
> `backend/gamesData/` folder existed on the `main` branch and were **deleted** when uploads
> moved to the database. See [Game Assets](Game-Assets.md) for the current model.

## Connection

Configured in `backend/src/main/resources/application.properties`:

```properties
app.frontend-origin=${FRONTEND_ORIGIN:http://localhost:5173}

spring.application.name=backend
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/ludarium}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD}

spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false

server.servlet.session.timeout=30m
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax

spring.servlet.multipart.max-file-size=100MB
spring.servlet.multipart.max-request-size=105MB
```

| Environment variable | Required | Default |
| --- | --- | --- |
| `DB_PASSWORD` | **yes** | none — startup fails without it |
| `DB_URL` | no | `jdbc:postgresql://localhost:5432/ludarium` |
| `DB_USERNAME` | no | `postgres` |
| `FRONTEND_ORIGIN` | no | `http://localhost:5173` |

Two settings are worth calling out:

- `ddl-auto=validate` — Hibernate never creates or alters a table. If a migration and an
  entity disagree, the application refuses to start.
- `open-in-view=false` — the `SecurityContext` cannot trigger lazy loading outside a
  transaction. Services must fetch what they need explicitly.

## Migrations

All migrations live in `backend/src/main/resources/db/migration/` and run automatically on
startup.

### V1: create_users

```sql
CREATE TABLE app_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(30) NOT NULL UNIQUE,
    email VARCHAR(254) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

The table is called `app_user` rather than `user` because `user` is reserved in PostgreSQL.

### V2: create_games

```sql
CREATE TABLE games (
    id VARCHAR(36) PRIMARY KEY,
    owner_id BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    title VARCHAR(120) NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    cover_image_url VARCHAR(500),
    entry_file VARCHAR(500) NOT NULL DEFAULT 'index.html',
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT'
        CHECK (status IN ('DRAFT','PUBLISHED')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_games_owner_id ON games(owner_id);
CREATE INDEX idx_games_status ON games(status);

CREATE TABLE game_files (
    game_id VARCHAR(36) NOT NULL REFERENCES games(id) ON DELETE CASCADE,
    path VARCHAR(500) NOT NULL,
    content_type VARCHAR(150) NOT NULL,
    content BYTEA NOT NULL,
    PRIMARY KEY (game_id, path)
);
```

`game_files` is the key design decision of the project: **the game's binary files live in the
database** as `bytea` rows, keyed by `(game_id, path)`. The composite primary key makes
serving an asset a single indexed lookup, and `ON DELETE CASCADE` means removing a game
removes its assets automatically.

### V3: add_user_description

```sql
ALTER TABLE app_user
    ADD COLUMN description VARCHAR(500);
```

### V4: search_trigram

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_games_title_trgm ON games USING GIN (upper(title) gin_trgm_ops);
CREATE INDEX idx_app_user_username_trgm ON app_user USING GIN (upper(username) gin_trgm_ops);
```

These GIN indexes are what make the `ILIKE '%term%'` lookups in
`GameRepository.findByTitleContainingIgnoreCase` and
`UserRepository.findByUsernameContainingIgnoreCase` fast. The `upper()` in the index
expression mirrors the case-insensitive comparison.

> `CREATE EXTENSION` requires a PostgreSQL superuser. If the app's `DB_USERNAME` is not
> privileged, this migration fails. See [Getting Started](Getting-Started.md).

### V5: create_comments

```sql
ALTER TABLE app_user
    ADD COLUMN profile_image_url VARCHAR(500);

CREATE TABLE comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    game_id VARCHAR(36) NOT NULL REFERENCES games(id) ON DELETE CASCADE,
    author_id BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    parent_comment_id BIGINT REFERENCES comments(id) ON DELETE CASCADE,
    content VARCHAR(1000) NOT NULL,
    rating INTEGER,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_comments_rating CHECK (rating IS NULL OR rating BETWEEN 1 AND 5)
);

CREATE INDEX idx_comments_game_id ON comments(game_id);
CREATE INDEX idx_comments_parent_comment_id ON comments(parent_comment_id);
```

`parent_comment_id` is nullable: `NULL` means a root comment. The `chk_comments_rating`
constraint duplicates the `@Min(1) @Max(5)` bean validation so the invariant holds even if a
row is written outside the API.

## Entity model

### `User` → `app_user`

| Field | Column | Notes |
| --- | --- | --- |
| `id` | `id` | `Long`, IDENTITY |
| `username` | `username` | unique, max 30 |
| `email` | `email` | unique, max 254 |
| `passwordHash` | `password_hash` | prefixed hash, max 255 |
| `description` | `description` | nullable, max 500 |
| `profileImageUrl` | `profile_image_url` | nullable, max 500 |
| `createdAt` | `created_at` | not updatable |

### `Game` → `games`

| Field | Column | Notes |
| --- | --- | --- |
| `id` | `id` | `String`, app-generated `UUID.randomUUID().toString()` |
| `owner` | `owner_id` | `@ManyToOne(LAZY, optional = false)` to `User` |
| `title` | `title` | max 120 |
| `description` | `description` | `text`, defaults to `""` |
| `coverImageUrl` | `cover_image_url` | nullable; set to `/api/games/{id}/cover` on upload |
| `entryFile` | `entry_file` | defaults to `"index.html"` |
| `status` | `status` | `DRAFT` or `PUBLISHED`, stored as `STRING` |
| `createdAt` | `created_at` | not updatable |

> `Game` has **no setters for title or description**. A game is immutable after upload; only
> `assignOwner(User)` and `publish()` mutate it.

### `GameFile` → `game_files`

Uses a composite key:

```java
@Embeddable
public class GameFileId implements Serializable {
    private String gameId;
    private String path;
}
```

| Field | Column | Notes |
| --- | --- | --- |
| `id` | — | `@EmbeddedId GameFileId` |
| `game` | `game_id` | `@MapsId("gameId")`, `@ManyToOne(LAZY)` |
| `contentType` | `content_type` | sniffed at upload time, max 150 |
| `content` | `content` | `byte[]`, `columnDefinition = "bytea"` |

The cover image is **not** a column on `games`. It is stored as an ordinary row at the
reserved path `__metadata__/thumbnail`, which is why `GameCoverController` can reuse the same
repository lookup as the game files.

### `Comment` → `comments`

| Field | Column | Notes |
| --- | --- | --- |
| `id` | `id` | `Long`, IDENTITY |
| `game` | `game_id` | `@ManyToOne(LAZY, optional = false)` |
| `author` | `author_id` | `@ManyToOne(LAZY, optional = false)` |
| `parentComment` | `parent_comment_id` | self-reference, nullable |
| `content` | `content` | max 1000 |
| `rating` | `rating` | nullable, 1-5 |
| `createdAt` | `created_at` | not updatable |

Helpers `isRoot()` and `rootComment()` implement the one-level-deep rule: replying to a reply
rewrites the parent to the root, so the tree never grows past one level.

## Repositories

| Repository | Key queries |
| --- | --- |
| `UserRepository` | `findByEmailIgnoreCase`, `findByUsernameIgnoreCase`, `existsByEmailIgnoreCase`, `existsByUsernameIgnoreCase`, `findByUsernameContainingIgnoreCase(String, Pageable)` |
| `GameRepository` | `findByStatus(GameStatus, Pageable)`, `findByStatusOrderByCreatedAtDesc`, `findByOwner_IdNot`, `findByTitleContainingIgnoreCase(String, Pageable)` |
| `GameFileRepository` | `findById_GameIdAndId_Path(gameId, path)` |
| `CommentRepository` | `findByGame_IdAndParentCommentIsNullOrderByCreatedAtDescIdDesc`, `findByGame_IdAndParentCommentIsNotNullOrderByCreatedAtAscIdAsc` — both with `@EntityGraph(attributePaths = "author")` to avoid N+1 on the author |

Two declared methods are currently unused: `GameRepository.findByOwner_IdOrderByCreatedAtDesc`
and `GameFileRepository.findAllById_GameId`.

## Transaction boundaries

`@Transactional` is applied per service method, not per repository:

| Class | Methods | Transaction |
| --- | --- | --- |
| `GameUploadService` | `upload` | `@Transactional` |
| `GameService` | `publish` | `@Transactional` |
| `CommentService` | `listByGame` | `@Transactional(readOnly = true)` |
| `CommentService` | `create`, `createReply` | `@Transactional` |
| `DevDataSeeder` | `run` | `@Transactional` |
| `UserProfileService` | `getProfile`, `updateDescription` | none — relies on the repository's own transaction |

`GameUploadService.upload` is one transaction covering the `games` insert and **all** the
`game_files` inserts. It also reads every file of the ZIP fully into memory before writing,
so a 100 MB upload transiently needs roughly 100 MB of heap.

## The `dev` profile seeder

`config/DevDataSeeder.java` is an `ApplicationRunner` annotated `@Profile("dev")`. It reads its
credentials from `application-dev.properties`:

```properties
app.seed.username=lucas2
app.seed.email=lucas2@gmail.com
app.seed.password=lucas222
```

On startup it:

1. Creates the seed user if `findByUsernameIgnoreCase` finds nothing (idempotent).
2. Reassigns every game owned by another user to the seed user, via `findByOwner_IdNot`.
3. Publishes every `DRAFT` game, via `findByStatusOrderByCreatedAtDesc`.

It logs a summary:

```text
Seed dev listo: usuario=lucas2 juegos reasignados=0 juegos publicados=3
```

Running it twice does not duplicate the user. It is only active when the `dev` profile is
enabled explicitly, so it never touches a production database — though the plaintext
password is committed to the repository. See [Known Issues](Known-Issues.md).

## Inspecting the data

```bash
psql -U postgres -d ludarium -c "\dt"
psql -U postgres -d ludarium -c "SELECT id, title, status FROM games ORDER BY created_at DESC;"
psql -U postgres -d ludarium -c "SELECT game_id, path, length(content) FROM game_files LIMIT 10;"
psql -U postgres -d ludarium -c "SELECT username, email, description FROM app_user;"
```

To reset the local database, drop and recreate it and restart; Flyway will re-apply V1-V5:

```bash
dropdb -U postgres ludarium
createdb -U postgres ludarium
```

## Editing a migration that already ran

Flyway refuses to start when a checksum in `flyway_schema_history` no longer matches the file
on disk. There is no Flyway Maven plugin in `pom.xml`, so the practical fix for local
development is to drop and recreate the database:

```bash
dropdb -U postgres ludarium
createdb -U postgres ludarium
```

The rule of thumb: once a migration is on a shared branch, add a new `V<n>__...` file instead
of editing an existing one.
