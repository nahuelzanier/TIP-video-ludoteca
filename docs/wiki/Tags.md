# Game Tags

> **Status: not merged.** Everything on this page lives on `origin/feature/tags` (commits
> `0c642e7`..`623735a`). It is **not** on `main`, `dev` or `featureComentarios`. Nothing here
> is available on the deployed application yet.

Tags let any logged-in user describe a game with community labels (`Action`, `Puzzle`,
`Platformer`, ...). Tags are never created by users: the set is fixed by a migration and each
user can attach a tag to a published game once.

## Data model

Migration `V6__create_game_tags.sql` adds two tables:

```sql
CREATE TABLE tags (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(40) NOT NULL UNIQUE,
    slug VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE game_tag_assignments (
    game_id VARCHAR(36) NOT NULL
        REFERENCES games(id) ON DELETE CASCADE,
    tag_id BIGINT NOT NULL
        REFERENCES tags(id) ON DELETE CASCADE,
    user_id BIGINT NOT NULL
        REFERENCES app_user(id) ON DELETE CASCADE,
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_game_tag_assignments
        PRIMARY KEY (game_id, tag_id, user_id)
);

CREATE INDEX idx_game_tag_assignments_tag_game
    ON game_tag_assignments(tag_id, game_id);
```

The primary key is the whole rule set of the feature: a user can assign a given tag to a
given game at most once. There is no separate "tags on games" table and no `UNIQUE` beyond
the PK — `game_id + tag_id` alone is deliberately **not** unique, because three different
users voting "Puzzle" on the same game is the point.

`ON DELETE CASCADE` on all three foreign keys means deleting a game, a tag or a user removes
the corresponding assignments.

### The fixed catalogue

The migration seeds 15 tags:

```sql
INSERT INTO tags (name, slug) VALUES
    ('Action', 'action'),        ('Adventure', 'adventure'),
    ('Arcade', 'arcade'),        ('Fighting', 'fighting'),
    ('Horror', 'horror'),        ('Platformer', 'platformer'),
    ('Puzzle', 'puzzle'),        ('Racing', 'racing'),
    ('RPG', 'rpg'),              ('Roguelike', 'roguelike'),
    ('Shooter', 'shooter'),      ('Simulation', 'simulation'),
    ('Sports', 'sports'),        ('Strategy', 'strategy'),
    ('Casual', 'casual');
```

Because they are seeded by the migration, the ids are stable across environments only if the
migration runs against an empty `tags` table — which it does, since the table is created in
the same migration.

## The summary query

A game does not have tags; it has **tag assignments**, one per user. The read model collapses
them in a single JPQL query in `GameTagAssignmentRepository`:

```java
@Query("""
        SELECT new com.tip_video_ludoteca.tags.GameTagSummary(
            tag.id,
            tag.name,
            tag.slug,
            COUNT(assignment.id.userId),
            MIN(assignment.assignedAt)
        )
        FROM GameTagAssignment assignment
        JOIN assignment.tag tag
        WHERE assignment.id.gameId = :gameId
        GROUP BY tag.id, tag.name, tag.slug
        ORDER BY COUNT(assignment.id.userId) DESC,
                MIN(assignment.assignedAt) ASC,
                tag.name ASC
        """)
List<GameTagSummary> findTagSummariesByGameId(@Param("gameId") String gameId);
```

The result is ordered by **popularity first** (`COUNT` descending), then by how early the tag
was first used, then alphabetically. That makes the ordering stable and meaningful without a
curation step.

`GameTagSummary` is a record with exactly those five fields:

```java
public record GameTagSummary(
        Long tagId,
        String name,
        String slug,
        Long assignmentCount,
        Instant firstAssignedAt
) {}
```

## Endpoints

All four live in `controller/GameTagController.java`, mapped under `/api`.

### `GET /api/tags`

Public. The full catalogue, alphabetically by name.

```json
[
  { "id": 1, "name": "Action", "slug": "action" },
  { "id": 2, "name": "Adventure", "slug": "adventure" }
]
```

### `GET /api/games/{gameId}/tags`

Public. The collapsed summary list, ordered as described above.

```json
[
  {
    "tagId": 7,
    "name": "Puzzle",
    "slug": "puzzle",
    "assignmentCount": 3,
    "firstAssignedAt": "2026-10-02T09:15:00Z"
  }
]
```

Returns `404` if the game does not exist **or is not `PUBLISHED`**. A draft game is
indistinguishable from a missing one, which keeps unpublished games from being probed:

```java
private Game requirePublishedGame(String gameId) {
    Game game = games.findById(gameId)
            .orElseThrow(() -> new ResponseStatusException(
                    HttpStatus.NOT_FOUND, "Game not found."));

    if (game.getStatus() != GameStatus.PUBLISHED) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Game not found.");
    }

    return game;
}
```

### `GET /api/games/{gameId}/tags/mine`

**Requires a session.** This is the only tags route that is not public, and it needs its own
matcher placed *before* the `permitAll` block, because `/api/games/*/tags/mine` would
otherwise be swallowed by the broad `/api/games/**` rule:

```java
.requestMatchers(HttpMethod.GET, "/api/games/*/tags/mine").authenticated()
.requestMatchers(HttpMethod.GET,
    "/api/games", "/api/games/**", "/games/**",
    "/api/tags",
    "/api/search",
    "/api/users/*/profile",
    "/api/users/*/games",
    "/api/auth/csrf").permitAll()
```

Returns the bare ids the current user already assigned, so the UI can disable those buttons:

```json
[7, 12]
```

### `POST /api/games/{gameId}/tags`

Requires a session and a CSRF token.

```http
POST /api/games/3f9c2a41-7b5e-4c8d-9e10-2a6b8c4d1f35/tags
Content-Type: application/json
X-CSRF-TOKEN: 0d9f1c22-...

{ "tagId": 7 }
```

Returns `201 Created` with the **full updated tag list**, not just the created assignment, so
the client can replace its state in one step:

```json
[
  { "tagId": 7, "name": "Puzzle", "slug": "puzzle",
    "assignmentCount": 3, "firstAssignedAt": "2026-10-02T09:15:00Z" }
]
```

| Status | Cause |
| --- | --- |
| `201` | Tag assigned, body is the updated tag list |
| `400` | `A tag ID is required.` (null `tagId`) |
| `401` | No session, or `Authenticated user not found.` |
| `404` | `Game not found.` or `Tag not found.` |
| `409` | `You have already assigned this tag to this game.` |

The `409` is raised twice on purpose — once by an explicit existence check and once by
catching `DataIntegrityViolationException`, so two simultaneous requests from the same user
cannot both succeed:

```java
if (assignments.existsById_GameIdAndId_TagIdAndId_UserId(gameId, tagId, user.getId())) {
    throw new ResponseStatusException(
            HttpStatus.CONFLICT,
            "You have already assigned this tag to this game.");
}

try {
    assignments.saveAndFlush(new GameTagAssignment(game, tag, user));
} catch (DataIntegrityViolationException exception) {
    // También cubre dos solicitudes simultáneas del mismo usuario.
    throw new ResponseStatusException(
            HttpStatus.CONFLICT,
            "You have already assigned this tag to this game.",
            exception
    );
}
```

> These endpoints throw `ResponseStatusException`, so they return a `ProblemDetail` body
> rather than the `{"error":"..."}` envelope used elsewhere. See
> [Known Issues](Known-Issues.md).

## Frontend

`services/tagService.ts` exposes four functions mirroring the four endpoints:

| Function | Method | Path |
| --- | --- | --- |
| `getAvailableTags()` | `GET` | `/api/tags` |
| `getGameTags(gameId)` | `GET` | `/api/games/{id}/tags` |
| `getMyGameTagIds(gameId)` | `GET` | `/api/games/{id}/tags/mine` |
| `assignGameTag(gameId, tagId)` | `POST` | `/api/games/{id}/tags` |

Types:

```ts
export interface TagOption { id: number; name: string; slug: string; }

export interface GameTag {
  tagId: number;
  name: string;
  slug: string;
  assignmentCount: number;
  firstAssignedAt: string;
}
```

`components/games/GameTagSection.tsx` renders it. It loads four things in parallel with
`Promise.all` and only calls `getMyGameTagIds` when there is a session:

```tsx
const [allTags, assignedTags, currentUser] = await Promise.all([
  getAvailableTags(),
  getGameTags(gameId),
  getCurrentUser(),
]);

let ownTagIds: number[] = [];
if (currentUser) {
  ownTagIds = await getMyGameTagIds(gameId);
}
```

The section has three states:

- **Loading** — `"Loading tags..."`.
- **Signed out** — `"Log in to assign tags."` with a link to `/login`, carrying
  `state={{ from: `/game/${gameId}` }}` so the user returns to the game.
- **Signed in** — the list of assigned tags with their counts, plus a picker of all 15 tags.
  Buttons the user already assigned are disabled and marked with a `✓`, with the tooltip
  `"You have already assigned this tag."`.

`Game.tsx` places it between the player and the comments:

```tsx
<GameSection gameUrl={gameUrl} />
<GameTagSection gameId={game.id} />
<CommentSection gameId={game.id} />
```
